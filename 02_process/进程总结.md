# 进程总结

本章对应 fork_demo、exec_demo、pipe_ipc。它们都是独立的 Linux 用户态程序，分别学习创建、替换、等待和通信。

## 1. fork：创建子进程

fork 成功时，父子进程都从调用后的下一条语句继续执行：

| 返回值 | 所在执行流 | 后续处理 |
| --- | --- | --- |
| 大于 0 | 父进程 | 返回值是子进程 PID |
| 等于 0 | 子进程 | 用 getpid 获取自己的 PID |
| 等于 -1 | 父进程 | 创建失败，没有新子进程，读取 errno |

“调用一次、返回两次”只描述成功情况。父子进程的虚拟地址空间通常相互独立，Linux 一般通过写时复制降低 fork 的初始成本；这不意味着普通全局变量在 fork 后仍可用作共享通信。

文件描述符也会被继承，但对应的内核对象可能仍是同一个。例如本项目的管道：父子进程各自持有描述符，引用的是同一个内核管道。

fork 前应考虑用户态输出缓冲区。若缓冲内容尚未刷新，它可能被父子进程各刷新一次。本例在 fork 前使用 std::endl 输出并刷新，测试也会检查该行只出现一次。

## 2. waitpid：等待、回收与解释状态

父进程调用 waitpid(child_pid, &status, 0)，阻塞等待指定子进程。子进程退出后，内核会保留退出信息，直到父进程收集；在本例的默认信号处理下，遗漏回收会留下僵尸状态。

不能只初始化 status 就认为等待成功。必须先检查 waitpid 返回值：

~~~cpp
int status = 0;
pid_t waited;
do {
    waited = waitpid(pid, &status, 0);
} while (waited == -1 && errno == EINTR);
~~~

返回 -1 且 errno 为 EINTR 时重试；其他错误应报告并返回失败。仅在成功等待之后，才解释 status。

- WIFEXITED(status)：通过 return、exit 或 _exit 正常退出；再用 WEXITSTATUS 读取退出码。
- WIFSIGNALED(status)：因信号终止；再用 WTERMSIG 读取信号编号。
- status 是编码后的状态，不是直接的退出码。

本项目在子进程正常退出时传播其退出码，在信号终止时返回 128 + 信号编号。例如 SIGTERM 为 15，对应外层退出码 143。

父进程可以配置其他子进程回收策略，但本项目采用显式 waitpid，便于观察完整生命周期。

## 3. exec：替换程序映像

exec_demo 的流程：

~~~mermaid
flowchart TD
    A["启动 exec_demo"] --> B["fork"]
    B --> P["父进程：waitpid"]
    B --> C["子进程：execvp"]
    C --> L["执行 PATH 中的 ls -l -a"]
    L --> E["子进程结束"]
    E --> P
    P --> R["报告并返回子进程状态"]
~~~

exec 不创建新进程。它替换代码、数据和栈等程序映像，PID 保持不变，当前工作目录等部分进程属性也保留。成功时不会返回到原调用处；若程序继续执行 exec 后面的语句，就说明调用失败。

常见后缀：

| 后缀 | 含义 |
| --- | --- |
| l | 逐个列出参数 |
| v | 用以空指针结尾的参数数组 |
| p | 对不含斜杠的程序名按 PATH 搜索 |
| e | 显式传入环境变量数组 |

本例使用可写字符数组构造 argv，再以 nullptr 结束参数数组，避免把字符串字面量强转成可写指针。argv[0] 按惯例是程序名。

execvp 调用的是 PATH 中的 ls，不保证是某个固定绝对路径；它列出继承的当前工作目录，不是 exec_demo 二进制所在目录。

exec 失败时使用 perror 输出错误，然后 _exit(1)。_exit 不运行 atexit 回调，也不再次刷新继承的 stdio 缓冲区。父进程读取状态后也返回 1，使 shell 和测试能正确识别失败。

此例在单线程进程中调用 fork。把 fork 嵌入多线程程序时，子进程在 exec 前可安全调用的函数受到额外限制，不能直接照搬所有 C++ 输出与资源操作。

## 4. pipe：通过字节流通信

在 fork 前创建匿名管道，父子进程继承其文件描述符：

~~~mermaid
flowchart LR
    P["父进程 write：pipefd[1]"] --> K["内核管道缓冲区"]
    K --> C["子进程 read：pipefd[0]"]
~~~

fork 后应立即关闭不用的端点：

| 执行流 | 保留 | 关闭 |
| --- | --- | --- |
| 父进程 | 写端 pipefd[1] | 读端 pipefd[0] |
| 子进程 | 读端 pipefd[0] | 写端 pipefd[1] |

描述符本身不是传输的数据；它是当前进程引用内核对象的句柄。本例通过 fork 继承匿名管道，FIFO 等机制则允许进程通过文件系统名称打开通信端点。

### 成功、失败和 EOF

pipe 成功返回 0，失败返回 -1，因此错误判断必须是 pipe(pipefd) == -1。原来的 <= 0 会把成功也当成失败。

read 的返回值：

- 大于 0：本次实际读取的字节数，可能少于请求量。
- 等于 0：EOF。
- 等于 -1：失败；EINTR 表示本次读入数据前被信号中断，可重试。

空管道并不必然是 EOF。阻塞模式下，只要还有写端打开，读取空管道就会等待；所有写端关闭且已有数据被读完后才返回 0。

子进程若忘记关闭自己继承的写端，就可能一直等不到 EOF。父进程也必须先关闭写端再 waitpid，否则会形成“父进程等子进程结束，子进程等父进程关闭写端”的相互等待。

### 分块读取与完整写入

当前子进程每次最多读取 128 字节，每轮都重新调用 read。每一块按返回长度用 cout.write 输出，不追加字符串结束符，因此恰好读满 128 字节也不会写越界。

前缀只输出一次，消息内容可以跨任意多个读取块，EOF 后只追加一次换行。空消息也能正常结束。

父进程通过 write_all 循环写入：维护已发送偏移；部分写入后继续发送剩余内容；EINTR 时重试；其他错误或无进展则返回失败。所有分支都在结束前处理端点与子进程回收。

如果读端提前全部关闭，默认 SIGPIPE 行为会终止写入进程。本例忽略 SIGPIPE，让 write 返回 EPIPE，便于打印错误并继续回收子进程。这个设置局限于示例进程本身。

close 的处理与 read/write 不同：本项目以 Linux 为目标，close 即使返回 EINTR 也不重试，避免误关已被复用的文件描述符。

## 5. 验收与观察

~~~bash
./build/fork_demo
./build/exec_demo
./build/pipe_ipc "hello"
./build/pipe_ipc ""
cmake -E chdir build ctest -L process --output-on-failure
cmake -E chdir build ctest -L pipe --output-on-failure
~~~

测试覆盖：

- 父子 PID 的对应关系和正常回收。
- ls 使用当前工作目录并显示隐藏文件。
- PATH 中找不到命令时返回 1。
- 用临时 ls 替身返回 7，确认父进程也返回 7。
- 用临时 ls 替身接收 SIGTERM，确认父进程返回 143。
- 管道消息长度为 0、127、128、129、4096、65537 字节时精确传输。
- 中文、换行和 shell 特殊字符作为数据保持不变。
- 参数过多时输出使用说明并返回 2。

边界测试比较完整字节串，不假定一次 read 就收到完整消息。临时命令替身不会修改系统程序。测试不会通过固定 PID 或固定父子打印顺序来判断通过。

ASan/UBSan 的独立构建命令见根目录 README。这些正常、边界和 exec 失败测试没有穷举所有系统调用故障；例如资源耗尽导致的 fork/pipe 失败仍属于需要进一步故障注入验证的路径。
