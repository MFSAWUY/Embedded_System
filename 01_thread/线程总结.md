# 线程总结

本章对应 std_thread、pthread_demo 和 thread_sync 三个独立程序。推荐先按根目录 README 构建，再结合本章逐个运行。

## 1. 线程是什么

同一进程中的线程共享地址空间，可以访问同一个全局变量、堆对象和打开的文件；各线程有独立的执行位置、寄存器状态和栈。共享内存使数据传递方便，也要求程序协调并发读写。

在一个核心上，线程可以交替运行；在多个核心上，线程可能真正同时运行。线程数更多并不必然更快，调度、争锁和 I/O 都有成本。

| 接口 | std_thread | pthread_demo |
| --- | --- | --- |
| 标准 | C++ 标准库 | POSIX |
| 创建 | std::thread(函数, 参数...) | pthread_create |
| 入口参数 | 普通函数参数或 lambda 捕获 | 一个 void* |
| 返回结果 | 本例只打印；通常可使用共享结果或 future | 本例返回 ThreadData 的地址 |
| 等待 | thread.join() | pthread_join |
| 错误报告 | 通常抛出 std::system_error | 直接返回错误编号 |

std::thread 是跨平台接口。Linux 上的常见实现使用 pthread，但 C++ 标准不要求其他平台采用同一底层实现。

## 2. std_thread 的执行过程

1. 主线程输出自己的线程 ID。
2. 创建 t1 和 t2，各执行 worker(id, 3)。
3. 创建 t3，运行 lambda。
4. 主线程依次 join 三个线程。
5. 输出硬件并发数提示和完成消息。

线程创建完成后即可被调度；join 是等待，不是启动。即使主线程先等待 t1，t2 和 t3 也可能已经运行或结束。

仍然 joinable 的 std::thread 对象在析构时会调用 std::terminate()。这与“底层线程是否已经执行完”是两回事：线程执行结束后，仍需 join 或 detach 处理对象的生命周期。

本例的多次输出操作不组成一个原子日志事务，因此同一行内容可能交错。join 全部完成后的最终日志不再与工作线程竞争输出。hardware_concurrency() 只提供提示，可能返回 0，不能直接当作可靠的线程池大小。

## 3. pthread 参数与结果的生命周期

本例为每个线程准备一个 ThreadData，包含 id 和 result。主线程将其地址作为 void* 传入，工作线程转回 ThreadData* 后填写结果，并返回同一个地址。

pthread_join 通过第二个参数取得返回指针。成功 join 建立同步关系，因此主线程随后读取结果不需要再加锁。

必须满足：

- 参数对象在线程访问期间仍然存活。本例把它们放在 main 的栈上，并在返回前等待全部已创建线程。
- 两个线程分别写各自的 result，没有同时修改同一个对象。
- 不返回工作线程内部局部变量的地址；那个局部变量在线程函数返回后已失效。
- 不把整数结果强转成指针再转回来。结构体能清楚表达所有权和实际数据类型。

pthread_create 和 pthread_join 返回 0 表示成功，非零值本身就是错误编号。应将该编号传给 strerror，不能假定 errno 已被设置。

如果第二个线程创建失败，程序仍会 join 第一个线程再报告失败。若 join 意外失败，程序无法确认参数对象是否仍被访问，因此打印诊断后直接结束整个进程。pthread_join 不以 EINTR 报告信号中断，不应机械套用 read/waitpid 的重试方式。

pthread_t 是不透明类型，本例使用自己的 id 标识线程，避免跨平台假定 pthread_t 能按整数输出。

## 4. 生产者—消费者模型

两个生产者各依次放入 0～9，两个消费者各取出 10 个元素，共 20 个元素。共享队列容量为 5。

~~~mermaid
flowchart LR
    P1["生产者1：0～9"] --> Q["共享队列，容量5"]
    P2["生产者2：0～9"] --> Q
    Q --> C1["消费者1"]
    Q --> C2["消费者2"]
~~~

队列是 FIFO：消费顺序应与实际入队顺序相同。但两个生产者谁先入队、哪个消费者取到元素，由调度决定，不能假定输出总是某种排列。

互斥锁 mtx 保护所有共享队列操作，包括 push、pop、front、empty 和 size。size 虽然只读，也不能在其他线程可能修改队列时无锁调用。

### 条件变量如何等待

生产者的条件是队列未满，消费者的条件是队列非空。两者使用同一个互斥锁、同一个条件变量：

~~~cpp
cv.wait(lock, [] { return q.size() < MAX_QUEUE_SIZE; });
cv.wait(lock, [] { return !q.empty(); });
~~~

wait(lock, predicate) 的行为可以理解为：持锁检查条件；条件不满足时，原子地释放锁并进入等待；被通知或虚假唤醒后重新加锁，再次检查条件。返回时仍然持锁。

条件保存在共享状态中，而不是保存在通知里。notify 不会替线程取到数据，也不承诺唤醒后条件一定成立。带谓词的等待可以应对虚假唤醒，以及其他线程先一步修改条件的情况。

这里两类等待者共用一个条件变量，因此使用 notify_all。不能直接改成 notify_one：它可能只唤醒一个条件仍不满足的同类线程，让另一类线程继续睡眠。如果要针对性通知，应采用“非空”和“未满”两个条件变量。

### 临界区与解锁

每轮操作按以下顺序进行：

1. 通过 unique_lock 加锁。
2. 使用条件变量等待。
3. 修改队列并在锁内读取、打印修改后的大小。
4. 只解锁一次，通知其他线程。
5. 在锁外休眠，模拟工作耗时。

原代码在消费者中解锁两次，且两次之间无锁读取 size。当前已移除第一次解锁，让数据访问和日志都处于同一个临界区。

unique_lock 记录自己是否持有锁。手动 unlock 后，它的析构函数不会再次解锁；但再次显式调用 unlock 属于错误，会抛出 std::system_error。

## 5. 如何验证

从项目根目录执行：

~~~bash
./build/thread_sync
cmake -E chdir build ctest -L thread --output-on-failure
~~~

自动化测试按日志重建队列的可观察操作历史，核对：

- 恰好 20 次入队、20 次出队。
- FIFO 顺序没有被破坏。
- 0～9 各生产、消费两次。
- 每个线程恰好完成 10 次操作。
- 每一步队列大小都与操作历史一致，并处于 0～5。
- 程序在时限内结束，最终队列为空。

ThreadSanitizer 命令见根目录 README。日志验收检查功能行为，TSan 检查实际执行路径中的竞争，两者用途不同。

## 6. 后续练习

当前示例故意保留固定次数模型。若消费者总需求多于生产总量，消费者可能永远等待；如果消费者过早全部结束而队列又满了，生产者也可能永远等待。

可以进一步增加受同一把锁保护的“生产结束”状态：最后一个生产者设置结束状态并通知；消费者等待“队列非空或生产结束”，仅在“生产结束且队列为空”时退出。这里还没有实现该扩展，修改线程数量和任务数量时仍需遵守原有配额。

另一个练习是处理部分 std::thread 创建失败时的资源清理。普通 joinable 线程需要安全等待；生产者—消费者模型还需要取消或关闭机制，不能在缺少消费者时仅盲目 join 阻塞的生产者。
